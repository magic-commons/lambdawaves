# Iteration 025 — Deterministic audio-reactive render (offline analysis, MP4 audio, timestamp discipline)
Date 2026-10-28. Tags: [V] verified from the cited source, [I] inferred/derived. Scope: vanilla ES modules, Chromium + Firefox, WebCodecs → own muxer, PNG fallback.

## 0. What "no latency" means (the contract the builder implements)
- Frame i is rendered at t_i = i·den/num seconds (fps = num/den) + user offset. Its modulation value M_i is computed OFFLINE from the decoded PCM of the same file, over the window ending exactly at sample s_i = round(t_i·sr). No AnalyserNode, no AudioContext clock, no rAF: the live path's latencies (below) are NOT replicated. [I]
- The audio track muxed into the MP4 is the same PCM (or a bounce of it) starting at presentation time 0 = t_0, so the modulation the viewer sees at t and the sound they hear at t come from the same sample index. [I]

## 1. Offline audio analysis that reproduces AnalyserNode
Decode: `new AudioContext().decodeAudioData(buf)` resamples to the context rate; use `new OfflineAudioContext({numberOfChannels, length, sampleRate: sr})` and `decodeAudioData` on it to decode at a chosen sr (48000 recommended, see §4). OfflineAudioContext "does not render to the audio hardware", "renders as quickly as possible" to an AudioBuffer; suspend(t) is quantised to the 128-frame render quantum; AnalyserNode functions on a suspended context "MUST return the same data". [V] https://webaudio.github.io/web-audio-api/  https://developer.mozilla.org/en-US/docs/Web/API/OfflineAudioContext
A recording (MediaRecorder blob / captured PCM) goes through the same decode, so both sources become one Float32 PCM array + sr. [I]

AnalyserNode spec semantics to re-implement (Web Audio API §1.8, verified against Chromium `realtime_analyser.cc`): [V]
- fftSize N: power of two 32..32768, default 2048; "current time-domain data is the most recent fftSize sample-frames" (the N samples BEFORE the render head, oldest first; Chromium: `input_buffer.subspan(write_index - fft_size, fft_size)`).
- Down-mix to mono first: as if channelCount 1, channelCountMode "max", channelInterpretation "speakers" → stereo→mono = 0.5·(L+R). [V]
- Blackman window: α = 0.16, a0 = (1−α)/2 = 0.42, a1 = 0.5, a2 = α/2 = 0.08; w[n] = a0 − a1·cos(2πn/N) + a2·cos(4πn/N), n = 0..N−1 (periodic form, divide by N not N−1). [V]
- FFT: X[k] = (1/N)·Σ x̂[n]·e^(−2πi kn/N); only bins 0..N/2−1 kept; magnitude |X[k]| (Chromium `magnitude_scale = 1/fft_size`, no window-gain compensation). [V]
- Smoothing: X̂[k] = τ·X̂prev[k] + (1−τ)·|X[k]|, τ = smoothingTimeConstant (default 0.8), state zeros at start and after fftSize change, NaN/∞ → 0. [V]
- dB: Y[k] = 20·log10(X̂[k]). Byte: b[k] = floor(255/(maxDb−minDb)·(Y[k]−minDb)) clamped 0..255; defaults minDecibels −100, maxDecibels −30. Byte time-domain: floor(128·(1+x)). getFloatTimeDomainData returns the raw (unwindowed) last N samples. [V]
- The FFT is recomputed only when the analyser's current time has advanced (Chromium `if (current_time > last_analysis_time_)`), otherwise cached data is returned; i.e. live smoothing is applied once per CALL at the caller's rate (rAF ≈ display Hz), not per render quantum. [V]
Offline rule set: [I]
- Frame window: samples [s_i − N, s_i) (causal; identical to what the live analyser reads when the render head is at t_i). If s_i < N, zero-pad on the left (same as a fresh live buffer).
- Apply the smoothing recursion exactly once per video frame, in frame order; initialise X̂prev = 0 at the render start. Live smoothing runs at ~display Hz; to keep the same time constant at render fps use τ_fps = τ_display^(f_display/fps) (τ=0.8@60Hz → 0.716@30fps). Expose both "match preview (τ_fps)" and "raw τ".
- Bands/RMS/peak from the same window: RMS = sqrt(mean(x²)), peak = max|x|; band energy = Σ|X[k]|² over bins k·sr/N ∈ [f_lo, f_hi). Do everything in Float64 and in one Worker; result = Float32Array[N_frames × features], cached by (file hash, sr, N, τ, fps, offset). Deterministic across machines (pure JS math, no Web Audio node graph) as long as the decoder output is identical — decoders may differ by LSBs between browsers (resampler/codec); store the feature table with the project if bit-exact repeatability across browsers matters, or decode WAV/PCM sources yourself.
- Tempo lock: BPM clock gives t_i; pass musical offsets (bars) through the same t→s mapping; never derive s_i from accumulated float dt.
Live-path latencies (why screen recording and live analysis lag): AudioContext.currentTime is "the time of the start of the next audio block to be processed"; outputLatency = device delay after that; getOutputTimestamp gives {contextTime, performanceTime} for mapping to performance.now(); baseLatency = graph processing latency. [V] https://webaudio.github.io/web-audio-api/#dom-audiocontext-getoutputtimestamp  https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/outputLatency  The analyser window's centre lags the head by N/(2·sr) (21 ms @ 2048/48k); rAF adds 0–1 display frame; the compositor adds ≥1 more; total live lag ≈ 20–80 ms, hardware dependent. [I] For the PREVIEW (not the render) compensate by sampling the audio-side time as `ctx.getOutputTimestamp().contextTime + (performance.now()−performanceTime)/1000` and choosing the window ending there; for the render nothing is compensated because nothing is late. [I]

## 2. Audio in the MP4
Encoder availability (2026): AudioEncoder AAC `mp4a.40.2` is "not supported in Firefox on any platform, or in any browser on desktop Linux"; Opus is the universal WebCodecs audio encoder; Safari 26+ has AAC. [V] https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API/Codec_selection  Field reports: Firefox 158 `isConfigSupported({codec:'mp4a.40.2'})` → false, opus → true; Chrome 151 on Linux rejects AAC. [V] https://github.com/emse-students/canari/pull/1832  https://github.com/safubuki/turtle-video/issues/224  → Always probe with `AudioEncoder.isConfigSupported` and fall back AAC → Opus-in-MP4 → WebM/Opus. [I]
AAC registration: `aac.format` "aac" (default, raw `raw_data_block()` chunks, AudioSpecificConfig delivered once in `decoderConfig.description`) or "adts"; chunks always type "key"; sampleRate/numberOfChannels in the decoder config are ignored when description is present. [V] https://www.w3.org/TR/webcodecs-aac-codec-registration/
Opus registration: `format` "opus" (default) or "ogg"; description optional = RFC 7845 Identification Header ("OpusHead"); `frameDuration` default 20000 µs; complexity default 9 desktop; application "audio". [V] https://www.w3.org/TR/webcodecs-opus-codec-registration/  Chrome's Opus encoder supplies an OpusHead description; pre-skip is bytes 10–11 little-endian (312 observed). [V mp4-muxer reads it there; 312 observed in mediabunny #444]
AAC priming (encoder delay) — the sync trap: AAC-LC is "2112 samples = 1024+1024+64" for Apple/AudioToolbox encoders [V] https://github.com/uupaa/AAC.js/wiki/encoderdelay; Chrome on macOS measured 2112 (delegates to the OS encoder), other reports ~1024 (FFmpeg/wasm/MediaFoundation class); WebCodecs exposes NO priming info: first chunk timestamp is 0, not negative, and the 2-byte ASC has no room for it. [V] https://github.com/Vanilagy/mediabunny/issues/444  Consequence without an edit list: audio plays 21–48 ms late (1024/2112 samples @48k). [V] https://github.com/Vanilagy/mediabunny/issues/582  CMAF/ISO: an edit list SHOULD cover audio before presentation time 0 (priming). [V] https://trac.ffmpeg.org/ticket/10463 (title/summary via search)
Fix used by mediabunny #580 (merged 2026-10-28): "AAC priming delay is detected empirically in each machine", edit list + `roll` sample group written, negative start timestamps supported, Opus default pre-skip 3840→312, `getPreRollDuration()`. [V] https://github.com/Vanilagy/mediabunny/pull/580  Players: an elst alone over-trimmed in Adobe Audition; adding sgpd/sbgp `roll_distance = −1` (AAC-LC) made Audition, Audacity and ffmpeg all agree. [V] #444
Boxes for a second (audio) trak (what mp4-muxer/mediabunny write): [V] https://raw.githubusercontent.com/Vanilagy/mp4-muxer/main/src/box.ts  https://github.com/Vanilagy/mediabunny/blob/main/src/isobmff/isobmff-boxes.ts
- trak → tkhd (volume 1.0, width/height 0) → mdia → mdhd (timescale = sampleRate; Opus: 48000), hdlr 'soun', minf → smhd, dinf/dref/url, stbl → stsd, stts, stsc, stsz, stco/co64 (stss omitted: all samples sync).
- stsd/mp4a: channelcount, samplesize 16, samplerate 16.16 fixed; child `esds`: ES_Descriptor tag 3 (ES_ID 1) → DecoderConfigDescriptor tag 4: objectTypeIndication 0x40, streamType byte 0x15, bufferSizeDB u24, maxBitrate, avgBitrate → DecoderSpecificInfo tag 5 = description bytes verbatim → SLConfigDescriptor tag 6 = 0x02. (mp4-muxer encodes tag lengths as 0x80 0x80 0x80 len.)
- stsd/Opus: entry type 'Opus' + `dOps`: Version 0, OutputChannelCount u8, PreSkip u16, InputSampleRate u32, OutputGain s16 (8.8), ChannelMappingFamily u8 (0 for ≤2 ch, no table). Opus-in-ISOBMFF: mdhd timescale "typically 48000", mvhd timescale recommended equal to it; PreSkip is informative, "that task falls on the Edit List Box"; each Opus track needs sgpd+sbgp 'roll' and the 'iso2' compatible brand; roll_distance negative, covering ≥80 ms pre-roll (−4 for 20 ms packets [I]); last sample duration = only its valid samples. [V] https://opus-codec.org/docs/opus_in_isobmff.html
- edts/elst (both tracks, version 0 unless >32-bit): audio: one entry {segment_duration = (totalSamples − priming)·mvhdTimescale/sr, media_time = priming (in TRACK timescale), media_rate 1.0}; video: media_time 0 or omit. mediabunny: negative start offset → single trimming entry; positive → empty edit (media_time −1) then media. [V] isobmff-boxes.ts
- sgpd(grouping_type 'roll', version 1, default_length 2, one AudioRollRecoveryEntry roll_distance = −1 AAC / −4 Opus@20ms) + sbgp('roll', one run covering all samples, group_description_index 1). [V spec requirement; values I]
- stts: AAC one run {count = packets, delta = 1024}; Opus {delta = 960 @48k}. stsc/stco: interleave by chunks of ≈0.5 s presentation time per track (mp4-muxer cuts a new chunk at ≥0.5 s; mediabunny waits for all tracks before writing a timestamp). Write video chunk then the audio chunk covering the same span, so the moov's stco for both tracks points into an interleaved mdat. [V] https://raw.githubusercontent.com/Vanilagy/mp4-muxer/main/src/muxer.ts  https://mediabunny.dev/guide/writing-media-files
- Total sample count: feed the encoder exactly S = N_frames·sr·den/num samples (pad with silence to a whole packet); drop/trim the trailing packet per the elst segment_duration. [I]
- Fragmented vs flat: fragmented (moof/mdat, mvex/trex, tfdt) lets the browser stream to disk without holding mdat, but elst+fragments confuses VLC (QuickTime/Chromium/mediabunny are fine) and the duration is unknown until mfra. [V] https://github.com/Vanilagy/mediabunny/issues/444 (VLC note via search) For a deterministic offline render prefer a FLAT mp4 with `moov` written last (reserve mdat size, patch header) or `fastStart: 'in-memory'` style (moov first, computed offsets). [I]
WebM/Opus (simplest sync story): webm-muxer writes TimestampScale 1e6 (1 ms ticks), block ts = floor(µs/1000), CodecPrivate = OpusHead; it does NOT write CodecDelay/SeekPreRoll. [V] https://raw.githubusercontent.com/Vanilagy/webm-muxer/main/src/muxer.ts  Matroska requires: CodecDelay = pre-skip·1e9/48000 ns, SeekPreRoll = 80 000 000 ns, Channels/SamplingFrequency from OpusHead. [V] https://www.matroska.org/technical/codec_specs.html  Drawback: 1 ms ticks cannot express 1/30 s exactly (33.333 ms) → ±0.5 ms jitter in PTS unless TimestampScale is lowered (e.g. 1000 ns ticks) [I]; MP4 with timescale = fps numerator has zero jitter.

## 3. Timestamp discipline
- VideoFrame/AudioData timestamps are integer microseconds; `timestamp` is required for the canvas form of `new VideoFrame(canvas, {timestamp, duration})`. [V] https://developer.mozilla.org/en-US/docs/Web/API/VideoFrame/VideoFrame  Compute ts_i = Math.round(i·1e6·den/num) from the INTEGER frame index (never accumulate dt); duration_i = ts_{i+1} − ts_i. Exact in doubles below 2^53. [I]
- In the muxer do NOT convert µs → timescale; derive stts directly: video mdhd timescale = num (30000 for 29.97, 30 or 60 for integer fps; use 90000 only if num is unknown), every delta = den (1001 or 1). mediabunny: "use 24000/1001, 30000/1001, 60000/1001" exact forms, frames are snapped to the declared rate. [V] https://mediabunny.dev/guide/writing-media-files  mp4-muxer: rounds each delta and accumulates integer deltas to avoid drift; `firstTimestampBehavior` 'strict' throws if the first DTS ≠ 0, 'offset' shifts per track (can misalign A/V), 'cross-track-offset' uses the minimum. [V] muxer.ts
- AudioData for the encoder: timestamp_j = round(j·frameSize·1e6/sr) for the j-th block of PCM starting at sample 0 (f32-planar, sr = file sr; AAC encoders take 44.1 k/48 k, Opus 48 k). Encoded chunk timestamps come back ≈ input timestamps (AAC first chunk = 0, see §2). [V] #444
- Keyframes: `encode(frame, {keyFrame: i % G === 0})`, G = 1–2 s of frames (30/60); first frame key. Chromium's HEVC-on-AMD mislabels the first chunk "delta" (won't fix) — trust your own schedule, not chunk.type, for stss. [V] https://www.remotion.dev/docs/mediabunny/webcodecs-bugs
- What breaks players: first video PTS ≠ 0 without an edit list; audio priming not declared (A late by 21–48 ms); mixed timescales rounded through µs (29.97 drift); duration of last sample wrong (mp4-muxer only writes the preceding delta); edit list missing on video but present on audio with a different mvhd rounding ("Round separately to match the edit list" in mediabunny). [V] muxer.ts / isobmff-boxes.ts
- Firefox vs Chromium VideoEncoder, 2026: Firefox AVC encoder "shifts EncodedVideoChunk timestamps by their duration" (bug 2082890, open) and writes an invalid avcC on Windows/Linux (bug 2082867, open; one project rebuilds the avcC because SPS/PPS first byte is duplicated); Firefox converts RGB→I420 with the BT.601 limited matrix but tags BT.709 (bugs 2057760, 2056028; 157 adds colour signalling); Firefox has no 'quantizer' bitrate mode (bug 1871457 open). Chromium: `encodeQueueSize` "behaves unpredictably after encode()" (won't fix), 'quantizer' mode has a long first-chunk delay (open), performance collapses if the page re-renders during encode (open), encoder errors after flush() were swallowed before 152. [V] https://www.remotion.dev/docs/mediabunny/webcodecs-bugs  https://github.com/zenfully-org/zen-recorder/issues/37  https://github.com/emse-students/canari/pull/1832  https://bugzilla.mozilla.org/show_bug.cgi?id=1871457
- Config knobs (MDN): `latencyMode` "quality" (default, optimise quality) vs "realtime" ("may even drop frames to honor framerate") → always "quality" for renders; `bitrateMode` "constant" | "variable" (default) | "quantizer" (per-frame `avc.quantizer` 0–51, ignores bitrate); `hardwareAcceleration` "no-preference" | "prefer-hardware" | "prefer-software" — Chromium treats prefer-* as requirements, no-preference silently falls back; `avc.format` "avc" (default; SPS/PPS only in `decoderConfig.description` = AVCDecoderConfigurationRecord → copy into avcC) vs "annexb" (in-band, no description). [V] https://developer.mozilla.org/en-US/docs/Web/API/VideoEncoder/configure  https://www.w3.org/TR/webcodecs-avc-codec-registration/  https://lists.w3.org/Archives/Public/public-webrtc-logs/2022Feb/0153.html  Reproducible bits run-to-run need the software encoder (`prefer-software`); hardware encoders are not bit-reproducible and vary by GPU. [I]

## 4. The DAW/NLE model
- Offline bounce = the engine runs its own sample clock faster than real time; automation is evaluated per block/sample from the timeline, never from wall time; Pro Tools advertises "Sample Accurate Offline Bounce (~150× realtime)". [V(forum)/I] https://www.production-expert.com/production-expert-1/4-ways-to-bounce-audio-from-your-daw  Browser equivalent = OfflineAudioContext (if the app needs effects) or plain PCM math (features only), both driven by sample index. [I]
- "Render in place" (Cubase) / freeze = bounce a track's processed audio to a clip at the same timeline position, so later stages read fixed samples — the analogue of caching the feature table per frame. [I]
- NLE frame lock: audio keeps its own sample clock; video frames are addressed as sample spans. 48 kHz/30 fps = 1600 samples per frame exactly; 29.97 = 1601.6 → NTSC 5-frame cadence 1602,1601,1602,1601,1602 (= 8008 samples per 5 frames) as coded in FFmpeg's MXF muxer; 59.94 = 801,801,801,801,800. [V] https://lists.ffmpeg.org/pipermail/ffmpeg-cvslog/2014-March/074670.html  https://ffmpeg.org/pipermail/ffmpeg-devel/2018-May/230578.html  Hence: audio track timescale = sr, video timescale = num; never force audio into frame-sized packets. [I]
- Musical time: with BPM b, beat k is at t = 60k/b; frame i covers [t_i, t_{i+1}); sample-accurate beat phase for frame i = frac((s_i/sr)·b/60). [I]

## 5. Common artefacts and cures
- Dropped/reordered frames: never let `encodeQueueSize` grow unbounded; await a `dequeue` event (fires on decrease) when size > ~4–8, and await `flush()` before finalising; keep `latencyMode: 'quality'`. [V] https://developer.mozilla.org/en-US/docs/Web/API/VideoEncoder/dequeue_event  https://developer.mozilla.org/en-US/docs/Web/API/VideoEncoder/encodeQueueSize  Because Chromium's queue size is unreliable after encode(), also cap the number of in-flight frames by counting `output` callbacks. [V/I]
- Stalls: `frame.close()` right after `encode()`; call `encode` only with the frame created from the finished WebGPU canvas (await `device.queue.onSubmittedWorkDone()` before `new VideoFrame(canvas)`), or `copyExternalImageToBuffer`→ `new VideoFrame(buffer,{format:'RGBA',colorSpace:{...}})`. [I]
- Colour/range: a canvas VideoFrame is RGB; the encoder converts to limited-range BT.709 (Chrome 154 honours the frame's declared colorSpace; Firefox uses BT.601 but tags 709 → tag your Firefox output BT.601 or convert to I420 yourself with BT.709 and feed a YUV VideoFrame). Decoder configs come back {bt709, bt709, bt709, limited}. Write `colr` (nclx 1,1,1, full_range 0) in avc1 so players don't guess; untagged HD → some players assume 709, others 601 → washed/shifted colour. [V] https://github.com/CyberAgentGameEntertainment/InstantReplay/pull/173  https://github.com/Vanilagy/mediabunny/pull/553  https://github.com/zenfully-org/zen-recorder/issues/37  https://www.mux.com/blog/your-browser-and-my-browser-see-different-colors
- Dimensions: 4:2:0 encoders need even width/height; round the render target to even values (or pad) before configuring; hardware encoders reject very small or non-16-aligned sizes with EncodingError even when isConfigSupported said yes (Firefox realtime-H.264 on macOS fails the same way) → run a 2-frame probe encode in the self-test and fall back to prefer-software. [V] https://github.com/eshtek/spice-html5/pull/6 [I for evenness]
- Alpha: `alpha: 'discard'` (default) — MP4/H.264 has no alpha; composite onto the background first. [V] MDN configure
- Bitrate for noise/grain (dense high-frequency content, no temporal redundancy): H.264 VBR 1080p30 ≥ 20–30 Mbit/s, 1440p ≥ 40, 2160p ≥ 60–80; 60 fps ×1.5; or `bitrateMode:'quantizer'` with avc.quantizer 14–18 (Chromium; mediabunny blog shows quantizer encoding in browsers) — expect the first-chunk delay bug; AV1/VP9 need ~0.6× of that. [I] https://mediabunny.dev/blog/quantizer-support
- Fallback PNG+WAV → ffmpeg (exact; `-framerate` before `-i`; `-fps_mode cfr` duplicates/drops to exactly the requested rate; `-itsoffset` delays an input; `-shortest` ends at the shortest stream): [V] https://ffmpeg.org/ffmpeg.html  https://ffmpeg.org/ffmpeg-formats.html
  `ffmpeg -framerate 30000/1001 -start_number 0 -i frame_%06d.png -itsoffset 0 -i render.wav -map 0:v -map 1:a -vf "scale=out_color_matrix=bt709:out_range=tv,format=yuv420p" -color_primaries bt709 -color_trc bt709 -colorspace bt709 -color_range tv -c:v libx264 -preset slow -crf 16 -g 60 -fps_mode cfr -video_track_timescale 30000 -c:a aac -b:a 256k -shortest -movflags +faststart out.mp4`  (ffmpeg's aac encoder declares its own priming via edit list by default: `use_editlist auto`.) [V option names / I values]  WAV = the same PCM span [t_0, t_end) written offline, so `-itsoffset` stays 0; use `-itsoffset 0.0xx` only to apply a user's deliberate audio offset.

## 6. Recommended design (≤ 25 lines)
1. Audio source (file or recording) → one PCM asset {Float32 planar, sr = 48000 via OfflineAudioContext.decodeAudioData, hash}. Store alongside the project.
2. Feature worker: for each frame i compute s_i = round(i·den/num·sr) (+ user offset in samples); window [s_i−N, s_i); mono-mix 0.5(L+R); Blackman (α 0.16); FFT N; |X|/N; smoothing once per frame with τ_fps; dB 20log10; bands/RMS/peak. Output Float32Array table [frames × features]; cache by hash of (asset, N, τ, bands, fps, offset).
3. Preview path keeps the AnalyserNode but reads the window ending at the audio-output time (getOutputTimestamp) and labels itself "preview, ±1 frame"; the render never touches it.
4. Render loop: for i in 0..F−1: set clock to t_i, bind feature row i as the modulation values, draw to the WebGPU canvas, `await queue.onSubmittedWorkDone()`, `new VideoFrame(canvas,{timestamp: round(i·1e6·den/num), duration})`, back-pressure on dequeue/in-flight count, `encode({keyFrame: i%G===0})`, `close()`. `latencyMode:'quality'`, `avc.format:'avc'`, `hardwareAcceleration` per user (default no-preference, "reproducible" = prefer-software).
5. Audio encode in parallel from the same PCM: probe AAC (`mp4a.40.2`, 48 k, 256 kbit/s) → else Opus (48 k, 20 ms, 192 kbit/s) → chunk PCM into 1024/960-sample AudioData with timestamp round(j·frame·1e6/sr).
6. Priming: AAC — run a one-time calibration on this machine (encode 1 s with a single impulse at sample 24000, decode with AudioDecoder, onset − 24000 = priming; Chrome measured 1024 or 2112), persist per (browser, platform); write elst media_time = priming + sgpd/sbgp roll −1. Opus — pre-skip from OpusHead bytes 10–11, elst media_time = pre-skip, roll −4, brand iso2.
7. Muxer (own code): ftyp (isom, iso2, avc1/Opus, mp41) · mdat (reserved 64-bit size, patched) · moov {mvhd ts 1000 (or 48000 when Opus) · video trak ts=num, stts delta=den, stss from own schedule, avcC from description, colr nclx 1/1/1 limited · audio trak ts=sr, mp4a/esds or Opus/dOps, elst, sgpd/sbgp} with chunks interleaved per 0.5 s. Flat file, moov last; optional second pass to put moov first.
8. Fallbacks: no VideoEncoder/AudioEncoder → PNG sequence (frame_%06d.png) + render.wav + the §5 ffmpeg line written into a README.txt in the zip. Firefox H.264 → use VP9/Opus (WebM, CodecDelay/SeekPreRoll written) or AV1 in MP4 until bugs 2082890/2082867 close.
9. Settings that must be obeyed and their self-test (run on a 90-frame calibration project before the real render, decode the output with VideoDecoder/AudioDecoder):
   fps → mdhd.timescale/stts.delta == num/den and decoded frame count == F, each frame.timestamp == round(i·1e6·den/num);
   resolution → decoderConfig.codedWidth/Height == requested (even-rounded) and visibleRect unchanged;
   range/colour → a 16/235 grey ramp decoded back within ±1 code value, colr present;
   bitrate → bytes·8/duration within ±15 % of target (VBR) or avg QP reported;
   audio on/off → trak count 1 or 2; A/V alignment → white flash at frame k and a click at s_k: decoded click onset after elst == k·sr·den/num ± 1 sample (≤ 0.02 ms), i.e. zero latency by construction;
   determinism → two consecutive renders with prefer-software give identical SHA-256; with hardware, identical decoded frame timestamps and PSNR > 45 dB between runs.
10. Never: derive time from performance.now/rAF during a render, round µs→timescale, trust chunk.type for stss, or ship an AAC track without elst+roll.
